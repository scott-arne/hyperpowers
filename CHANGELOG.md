# Hyperpowers Changelog

This file records **this fork's own releases**. The fork's version stream is independent of upstream Superpowers and may collide numerically with upstream tags without sharing content; the current upstream base is recorded in [`.upstream-version.json`](.upstream-version.json). Upstream's release history is preserved unchanged in [RELEASE-NOTES.md](RELEASE-NOTES.md).

## Unreleased

- **Several sessions can work one plan, or sibling plans of one spec, at once.** Plans carry a `**Depends on:**` line per task (a plan without any is serial, as before); `sdd-state deps` reads the graph from the plan ref's head and `deps --check` names tasks that share files or interfaces without an edge; a session registers the plan's integration branch (`register`), asks `next` for the claimable frontier, claims a task and gets a task branch (`<integration>.<ws8>.task-N`), merges the approved commit back after its gate (`merge-back`, by the plumbing `sync` uses, under both repositories' locks, with a merge record that makes a retry idempotent), and claims the final train (`claim final`) with a lease on the branch that serializes sibling plans' finals; `wait` and `board` show who waits on what; `amend` is the plan ref's only writer; `finish` takes `--session`. Two sessions on one plan need this version on both.
- **The stop guard lets a waiting session end its turn.** A session that publishes its own waiting record during a turn (`sdd-state wait`, or `merge-back` stopping on a conflict) may end that turn, and the guard logs the allow as `waiting-record`. A record from an earlier turn, another session's record, or one whose `since=` is not a whole-second UTC time does not count; a record the hook cannot read is an allow logged as `hook-error`. A successful claim, the owner's retry of its own task or final claim included, clears the session's own record unless it names a merge, so a session that waited and then took a task in the same turn cannot end that turn on the old record. The guard counts only the session's own tracked jobs.
- **Smaller fixes to the multi-session helpers.** `complete` reads task headings from the plan ref's copy, skipping fenced blocks, and prints `status=invalid` for a plan that does not parse. `complete`, `handback`, `snapshot`, `wait` and `sync` accept `--code-repo`, as the skill's split-layout instruction asks of every call. Every machine-written ledger line goes through `hp_ledger_append`, so none glues to a half-written line. A ledger line counts as a task's completion only when it is the marker itself, list-marked or emphasized at most, so a quoted `> Task N: complete` or a `Task N: complete-not-yet` no longer reads as done. A final-train takeover after a finish killed past its rename-aside, before its removal was committed, puts the plan's workspace back and takes the plan over as an open one; beside a new or recreated workspace it names the copy and answers `busy`. A takeover reads a missing or malformed `closing=` in the replaced lease as closing, so a damaged lease never reopens a branch being torn down. `amend` answers `checked-out` when another writer moved the plan ref during the amendment while a worktree has that ref checked out, instead of retrying over a worktree left at the old head. `amend` refuses while a worktree registered on the plan ref has lost its directory, naming the `git worktree prune` (or `unlock` and `prune`) that clears it. `amend`'s worktree refresh moves the plan file aside and checks it there before git writes the new plan, so a deletion made during the refresh is no longer written back. Waiting and activity records publish with one `rename(2)`, which refuses a directory created at the record's path rather than moving the record inside it. A plain-backend `snapshot --session` stamps activity under the plan lock, so it cannot recreate a workspace a finish removed meanwhile. `snapshot --session ''` is refused like any other invalid session id. Session ids may not hold whitespace or a colon, which would split the ledger's session line; `register` now checks the id too. The board skips `waiting/` and `activity/` entries whose names are not session ids, so a fetched name holding a newline shows no phantom sessions. A merge-back that stops on a conflict stamps the session's activity beside its waiting record, as `wait` does. `review-package` reads the objects as written, ignoring replace refs and grafts, and merge-back ignores grafts too, so reviewers see what merges and a graft cannot turn a divergent merge into a fast forward. `merge-back` and `amend` refuse a symbolic integration or plan ref, and their swaps no longer follow one made symbolic after that check. The approval line now carries the full commit id (`Task N: approved <full id>`), which merge-back compares whole and reads only from complete ledger records; a seven-character line reads as no approval, so a ledger in flight at upgrade re-appends one approval line per open task.
- **A second plan of one spec recompiles its records.** The spec's Outcome line names every plan with its date, each record's `Recorded:` lists them, and each plan's notes are their own paragraph; the finishing skill withholds the merge while a sibling plan is open on the branch and releases the branch lease after the option runs. The compiler refuses, before writing anything, notes that would replace another finish's notes, and it matches plan file names whole in the Outcome line and the notes sections.
- **Floors.** `merge-back` and `amend` need git 2.38 (`merge-tree --write-tree`) and refuse an older git by name; everything else keeps 2.31.

## 6.17.0 (2026-11-06)

In Zed, SDD sessions looked idle while the plan was unfinished, and a controller sometimes ended its turn after announcing its next step.

- **On Claude Code, the SDD stop guard refuses a turn end that leaves the plan unfinished.** A Stop hook, `hooks/sdd-stop-guard`, finds the session's SDD ledger and reads its plan when a turn is about to end. A turn that would end mid-plan with nothing tracked live is refused, and so is an immediate second attempt; a third consecutive attempt is allowed and logged as `cap`, and any allow resets the count. The refusal names the plan and what remains of it and tells the controller to take its next step in the same turn, or to run `sdd-state handback` when it is handing back to the human partner. A turn end with a background shell or a tracked job still running and no subagent live is refused the same way, naming the job and asking for a foreground `tracked-job wait`. The guard allows a turn end while a subagent is live, after a `handback` line written in that turn, after a final message that asks a question or reports BLOCKED, and in a session with no plan. Every decision for a session with a plan is logged with its reason, in the workspace's `stop-guard.jsonl` and a per-session mirror under `~/.cache/hyperpowers/stop-guard/`, unless the log itself cannot be written, and then the turn end is allowed. A record the hook cannot read is an allow, the hook exits 0 on every path, Codex and Cursor do not load it, and every skill path works without it.
- **The SDD skill states when a turn may end mid-plan.** While the plan has tasks left, a turn ends in exactly three cases: a BLOCKED status the controller cannot resolve, a question only the human partner can answer asked in that message, or, on a harness that cannot wait in the foreground, tracked work still running and named in that message. A message that names the next step is followed by that step's tool call in the same turn. Completing the last task opens the final whole-branch review, and the plan ends only after Finish. Each permitted turn end, and the human partner's request to stop, is written to the ledger with `sdd-state handback` in the message that ends the turn. Work that outlives one tool call starts through the harness's tracked background option, never with a trailing `&`, `nohup`, `setsid`, `disown` or a script that detaches a process.
- **Helpers write the records the guard reads.** `scripts/sdd-state complete PLAN_FILE N --commits <base7>..<head7>` appends a task's completion line to the ledger and snapshots it, and the controller repeats it until it prints `status=complete`. `sdd-state handback PLAN_FILE --reason "<why>"` writes a `handback` line for a permitted turn end: a question only the human partner can answer, a BLOCKED report, or their request to stop. `scripts/tracked-job` runs a command that may run past 10 minutes as a tracked job: `new` allocates the job and writes its `jobdir=` line in the ledger, `run` launches it under a supervisor that owns its process group, `wait` watches it in bounded foreground calls, and `stop` sweeps the group. A job's state is the `meta.json` in its directory under `<workspace>/jobs/`, and its output stays in `out.log`, out of the ledger. `sdd-state finish` adds `receipt=<path>` to its `finished` line: a copy of the ledger, the guard's log and the job records under `~/.cache/hyperpowers/receipts/` that outlives the workspace, kept until `sdd-state prune --receipts --days N --apply` removes it. Finish refuses (`status=live-jobs`) while a tracked job is still running, so its records are never removed under a live process.
- **On Claude Code, SDD waits in the foreground.** Implementer, reviewer, fix-round, re-review and final-review subagents are dispatched with `run_in_background: false`, and a covering command expected to finish within 10 minutes runs in the foreground, so the turn stays open while the work runs and Zed shows the session working; a longer command is a tracked job watched with `tracked-job wait`. A fix round on Claude Code now dispatches a fresh foreground implementer on the recorded model instead of resuming one, because a `SendMessage` resume let the turn end while the fix ran. The resume remains for harnesses without a foreground option, Claude Code's fork mode among them, where dispatches run in the background and the guard treats them as live work. Measured over ten scenario runs on Claude Code 2.1.317 (decision PASS): a foreground share of 1.0 (136 of 136 dispatches), both slow commands handled as the rule says in 10 of 10 runs, no untracked launch, no false refusal (`false_blocks_total` 0), and no premature stop reaching the human partner (`neither_listed_total` 0). The campaign's sessions never ended a turn mid-plan (`runs_with_plan_decisions` 0), so the guard's refusal ran live only in one Zed check. No campaign run needed a fix round; one Zed run is the only live case of the fresh foreground fix round. Evidence: hyperpowers-evals `evidence/2026-10-23-sdd-stop-guard/tally-z4b.txt` and `docs/hyperpowers/2026-10-23-sdd-stop-guard-eval-evidence.md`.

The SDD dossier follows the work between hosts.

- **A live broker is no longer called stale from a sandboxed shell.** `broker-health` read every failed `kill -0` as a dead pid, but a sandboxed shell gets EPERM for a process that exists; only ESRCH is death now, so the preflight stops offering a `broker.json` rename for a broker that is alive. The gate's index (codex-review-gate.md) says to run the preflight and every companion command outside the sandbox: a companion that cannot connect tears down the live broker's socket and record, which is how stale brokers were made.
- **An import keeps the legacy workspace.** After a verified import the old plain-cache workspace is set aside as `<path>.imported-<UTC>-<pid>` beside the pointer instead of deleted, so a session still on the previous plugin that appends to the old ledger writes into a copy a human can find; the plain-cache reclaim takes it with its root only once nothing under that root is newer than 14 days, and an import interrupted before the pointer is placed is completed by the next one.
- **`prune` reclaims the copies killed removals leave, in two steps.** A `plans/.removing-<ws>-<pid>` whose process is gone, older than `--days`, and for a workspace the branch does not track, is listed as `tombs=`; the first `--apply` renames it to `plans/.pruned-<ws>-<pid>` (a writer that still holds it open loses nothing), and a later `--apply` deletes it once nothing in it is newer than `--days`, listing it as `quarantined=`. Tracked copies still come back through `sync`. The transition is staged under `plans/.quarantining-<ws>-<pid>` so a crash never leaves a copy the next prune could delete, and a plan file whose name starts with a dot gets a workspace name without it, so no new workspace under `plans/` starts with a dot; a tracked path is never taken for a leftover, whatever its name.
- **The fetch stamp names its remote, branch and endpoint.** `<key>.fetched` now holds `<remote> <branch> <fingerprint of the fetch URL>`, and a checkout is created only when it names the configured `hyperpowers.stateRemote` and `hyperpowers.stateBranch` and the remote's current URL (a repointed remote asks for a sync); a `no-remote` sync leaves no stamp, so a remote added later asks for one `sync` first; a stamp from an earlier build is empty and asks for one `sdd-state sync`, after which it is current. The stamp names the endpoint the fetch contacted: the fetch is pinned to the URL that was fingerprinted (through git's environment configuration, git 2.31 or newer); a remote changed around the fetch, a repository that configures a remote under the pinned alias's own name, or a fingerprint that cannot be computed, ends the sync with `status=error` and nothing stamped, so creating a checkout in a repository with a remote now needs `node` (already required by `sdd-state`'s import, claim and recovery paths).
- **A plan's workspace lives on a state branch.** `sdd-dir` prints a workspace inside `~/.cache/hyperpowers/state/<key>/`, a checkout of the orphan branch `hyperpowers/state` kept once per clone and keyed by the clone's common git directory, so every worktree of a clone shares one live ledger. The ledger, reports, notes and claims are committed there and travel with the branch; briefs and review packages stay local and regenerate. The 6.16.0 pointer symlinks remain only in the plain cache, for cross-repository plans.
- **`sdd-state` carries the lifecycle.** `sync` fetches and reconciles (a fast-forward, a conflict-free merge with the ledger under the union driver, or `diverged` for the human partner to merge), never overwriting a live ledger; `verify` checks both ends of every completion range, the code repository's identity, and the plan version the ledger relies on; `snapshot` commits through a private index, with no hooks and no signing; `handoff --push` publishes after the optional scan named in `hyperpowers.prePushScan`, over every commit the push would publish; `finish` removes the plan's directory (the branch history keeps the dossier) and refuses open claims; inside the state checkout nothing is reclaimed automatically, and `prune`, which removes by age when asked, is the only other remover; the plain cache keeps its 14-day reclaim of idle roots, and `sync` removes a local workspace whose plan another host finished when it is unchanged since its last snapshot; `claim` is an atomic per-task claim for parallel sessions.
- **One branch question.** using-git-worktrees asks whether to stay on the current branch, create one in place, or use a worktree. That answer is the consent SDD used to require for main, and it is recorded per session in the ledger; finishing-a-development-branch takes it as its input.
- **Upgrade notes.** Both hosts need this version: an older plugin writes to the legacy cache and splits the ledger. A legacy workspace is imported on the first `sdd-dir` call and left as a symlink. Baselines that optimizing-performance stored under a linked worktree's old key are not moved. Codex gate directories and the ungated ledger are keyed by the common git directory from now on; `ungated-ledger pending` still reads the old key for one release. `sdd-dir` now refuses a plan file that does not exist, and refuses the plan form with `sdd-dir: node not found` where node is not on PATH; the no-argument form, which only prints the repository's plain-cache root, still works without it. The sandbox fallback (`backend=plain`) keeps a run working where `git worktree add` is refused, without portability. A plan file whose name begins with a dot continues in a new workspace; its earlier workspace, if the branch tracks one, stays on the branch under the old name. Such an earlier workspace holds the apply with `status=busy`, naming the file, while it carries a locally changed report that was never snapshotted (`snapshot_pending` skips dotted directories): revert the edit, commit it by hand on the state branch, or rename the workspace.

## 6.16.2 (2026-11-04)

Three changes cut the cost of long sessions without changing what the skills do.

- **SDD and brainstorming re-read the full skill after every context compaction.** Claude Code re-attaches each skill cut to its first 20,000 characters, which drops SDD's task loop from "3. Review the task" on and brainstorming's spec-writing steps. Both skills now tell the agent that a full Read made before a compaction does not survive it, and to Read the full skill after each compaction, the first and every later one, before its next action. Measured in a paired campaign at a forced 100000-token auto-compact window (evidence in `evals/evidence/2026-11-03-cost-reduction-6-16-2/`, note `docs/hyperpowers/2026-11-03-cost-reduction-6-16-2-eval-evidence.md`). The first wording ("after a compaction") re-read after only 92% of SDD and 75% of brainstorming compactions, so it was strengthened and the treatment arm re-measured:
  - Per-compaction re-read rate: SDD 98% (148 of 151), brainstorming 100% (20 of 20), control 0% (0 of 38 and 0 of 20). Seven of 10 SDD runs and 10 of 10 brainstorming runs re-read after every compaction.
  - Outcome: brainstorming 10 of 10 against the control's 10 of 10. SDD 9 of 10 against the control's 10 of 10: one run entered a loop of 13 compactions, each followed by a re-read, and finished only two of four tasks. That run is a tiny-window artifact. After a compaction the controller holds about 45K to 50K tokens, and re-reading SDD (about 10K) brings it back near the 100K window's threshold of about 67K. At the recommended 400K window there is about 300K of headroom.
  - Treatment SDD compacted more often than control at the forced window (151 times against 38) for the same reason. To be checked at 400K in the field re-measure.
  - README "Cost and Context" therefore says not to set the window below about 200K.
- **`gate-wait` watches every Codex job of a gate in one call.** The new script in `skills/requesting-code-review/scripts/` blocks in slices of at most 30 seconds with a full status sweep before each, within a 480-second default budget. The code-gate recipe, lens and findings docs use it, and document routes get its full path. The 16-minute watch cap is unchanged.
- **README "Cost and Context" recommends a compaction window.** It suggests `"autoCompactWindow": 400000` (a replay of a month of real sessions cut cost by about 28%; 300K and 200K saved 4 and 7 more points with 1.5 and 2.6 times the extra compactions), advises against going below about 200K because the skills re-read their full text after each compaction and a very small window can loop, recommends keeping `ENABLE_PROMPT_CACHING_1H=1` (a five-minute cache priced about 56% higher in the same replay), and suggests running `/clear` between a finished plan and SDD.

## 6.16.1 (2026-10-19)

Two bundled scripts misread the state they report on.

- **`stop-server.sh` treats only "No such process" as gone.** `process_exists` used to read every `kill -0` failure except "not permitted" as a dead process, so a failure nobody had listed discarded the session files of a live server. Now only ESRCH means gone, and any other failure is taken as alive. A pid file must hold a positive decimal pid no larger than 2147483647. An empty file, garbage, `0` or a negative number counts as no process: bash answers those with a usage error, `kill -0 0` signals the caller's own process group, and a negative number names a process group.
- **`gate-telemetry` counts the tasks of a plan run from another repository's checkout.** Since 6.16.0, `sdd-dir` keeps such a plan's workspace under the plan repository's key and leaves a symlink under the executing repository's key. The telemetry read only real directories, so the executing repository's row skipped those tasks. It now follows the link, skips a dangling one, and identifies a workspace by its real path. A row counts distinct task identities rather than brief files, the fleet totals count a workspace two rows reach once, and the fleet section reports the number of shared workspaces.

## 6.16.0 (2026-10-10)

Messages to the human partner reached for metaphors and contrasts that carried no fact.

- **A `communication` skill for prose a person will read.** `skills/communication/SKILL.md` states what a message to a person is (the answer first, only what the reader lacks, the specific thing in plain words, no contrast framing, ends on the last fact, shaped for a terminal). It gives a substitution table for the jargon metaphors that stand in for facts (blast radius, footgun, yak shaving, spine, seams, gate, belt-and-suspenders, long pole, load-bearing), removes every form of "not X but Y", and carries a check table of the strongest AI tells. `patterns.md` holds the full catalogue with before-and-after pairs, condensed from the humanizer skill (MIT) and Wikipedia's "Signs of AI writing". Measured with fresh single-shot subagents on three scenarios (an investigation report, a chat reply to a ship-or-fix question, a design-review critique), five reps per arm:
  - Figurative jargon from the list fell from 5 of 15 runs to 0 of 15; "load-bearing" from 2 to 0.
  - "Not X but Y" fell from 9 of 15 to 0 of 15.
  - Bold labels fell from 5 of 15 to 0 of 15; one-line restating closers from 6 of 15 to 0 of 15.
  - Dashes and headings were 0 of 15 in both arms under this harness, so those rules are unmeasured.
  - Every process skill that writes to the human partner carries a `REQUIRED SUB-SKILL: Use hyperpowers:communication` line at that point (brainstorming, writing-plans, subagent-driven-development, executing-plans, finishing-a-development-branch, requesting-code-review, receiving-code-review, systematic-debugging, dispatching-parallel-agents, profiling-performance, optimizing-performance), and `using-hyperpowers` routes "writing for your human partner" to it. Measured in live headless sessions with the worktree loaded as the plugin, five per scenario: the skill was invoked in 0 of 20 control sessions; with the lines, 5 of 5 brainstorming, 5 of 5 plan-writing, and 4 of 5 debugging sessions invoked it before the human-facing output, and 0 of 10 one-line or standalone-question sessions did. Where it was invoked right before a report, the bold labels disappeared; in brainstorming it fires a turn before the design presentation and the effect there is partial (2 of 5 presentations clean against 0 of 5). The bootstrap line did not make a standalone answer invoke the skill in either placement tried; it stays as a routing hint.

  Evidence: `docs/hyperpowers/2026-10-03-communication-skill-eval-evidence.md`; run artifacts in hyperpowers-evals under `evidence/2026-10-03-communication-skill/`.
- **The brainstorming companion server survives a sandboxed shell.** Under Claude Code's macOS sandbox a shell cannot run `ps` and cannot signal a process that another command started, so `stop-server.sh` read a live server as dead, reported `stale_pid`, and deleted its `server.pid` and `server-instance-id` while the server kept running. It now treats a process it may not signal as alive, and when it cannot read the process table it reports `unverified` (exit 1) and keeps the session files. `start-server.sh` leaves the owner watch off when `ps` cannot resolve the starting shell, so the idle timeout governs instead of a watch on the wrong process. `server.test.js` tears its server down when a test fails instead of leaving it running.
- **A single sentinel failure no longer holds a release by itself.** `CLAUDE.md` says so and points at the evals authoring guide's §5 rule: a sentinel failure is one sample of the scenario's base rate, a re-measure is owed only for a change a sentinel session reaches, and a regression needs a twenty-run rate whose Wilson lower bound clears the recorded base rate's upper bound. The planned severity cap for pathological review inputs was not shipped: the pre-registered control found no over-rating to cap (0 of 3 on fixtures P and P2). Evidence: `docs/hyperpowers/2026-10-03-review-calibration-and-sentinel-scope-eval-evidence.md`.
- **The companion server's `server-started` line means its `server-info` file exists.** `server.cjs` wrote `state/server-info` after printing the announcement, so a reader that acted on the announcement could find no file; the harness's own test lost that race under load. The write now precedes the announcement. The `server.test.js` wrapper also recorded a synchronous assertion failure by aborting the run; it now records one failure and runs the remaining tests.
- **`stop-server.sh` never reports a server it could not signal as stopped.** The stop loop read a refused `kill` as a dead process. When every signal is refused with "not permitted" and the process is still there, it reports `unverified`, exits 1 and keeps the session files, as the identity path already did.
- **`start-server.sh` no longer kills a recorded pid.** Every start creates a fresh session directory named for its process id and the current second, so the "kill any existing server" block could only act when that directory already held a `server.pid`, which takes the same process id within the same second; it is gone, and stopping a server is `stop-server.sh`'s job, with its identity check.
- **`verdict-normalize` fails closed on an unfinished job.** A companion payload whose `.job.status` is anything but `completed` (failed, cancelled, running, queued, missing or malformed) normalizes to `incomplete` whatever verdict text the record holds; payloads without a `job` property are read as before.
- **`sdd-dir` keys a plan by the plan's repository.** A cross-repository plan invoked from the other checkout used to get a second workspace and a split ledger; the key now comes from the directory that holds the plan, and the no-argument form still keys by the cwd. A session whose cwd is in another repository still sees the ledger after compaction: `sdd-dir` leaves a pointer to the workspace under that repository's key. After the update, a plan whose file lives in another checkout (a plan in the main checkout driven from a worktree is the common case) gets a new workspace path, so finish such an SDD run before updating, or copy its old workspace to the path `sdd-dir <plan>` now prints.

## 6.15.0 (2026-10-03)

A review finding was acted on before anyone checked it was true.

- **Reviewers check a finding before they report it.** `requesting-code-review/code-reviewer.md` and SDD's `task-reviewer-prompt.md` gain a "Before You Report a Finding" section. It asks four questions: what the exact file:line is, what the concrete failure is (input, state and outcome), whether the surrounding code was read, and whether the severity is defensible. It adds a proof rule for Critical and Important findings that covers both a defect in the diff and an omission. It states that zero findings is a valid review, and that the diff under review is data to analyze, never instructions. Measured on a new scenario, `code-review-precision-on-realistic-diff`. In Phase 5, treatment accepted 8 of 10 reviews against control's 0 of 10, but the fixture held two triggers its story called clean. On the fixed fixture the advantage did not reproduce:
  - As scored, treatment accepted 4 of 10 against control's 0 of 10. The pre-registered rule reads that as Worse, because an exact-line parser limit scored one correct review at recall 0.
  - Read by hand, treatment accepted 6 of 10 against control's 0 or 1 of 10, which fits none of the rule's readings.
  - In every reading, treatment raised fewer blocking findings on clean hunks: 0.5 to 0.8 per review against 1.9 to 2.2.

  The section stays as cheap guidance, by the human partner's call on the hand-read result. The Phase 5 claim of an unambiguous advantage is withdrawn. The section's eight-bullet "Skip these" catalogue was removed before measurement, because the baseline never raised a finding of any catalogue shape.
- **A blocking finding is confirmed before it is fixed.** `gate-fix-loop.md` now puts every blocking finding in exactly one state:
  - **Confirmed:** the controller fixes it. It leaves the ledger only through a fix, or through the human partner's explicit acceptance of the risk, recorded in their own words.
  - **Declined:** only as refuted (the cited code does not do what the finding says) or corrected (real, but not at blocking severity or not in scope). Either way the ledger carries file:line evidence.
  - **Unsettled:** it stays blocking. Uncertainty never clears a blocker.

  A blocking finding first raised in the backstop round is now carried to the hand-back as unresolved instead of declined. `gate-findings.md` defines when two lenses report the same defect: the same file and offending code, and the same failure. A matching title or line number does not make two findings the same defect. When findings merge, the strictest severity survives.
- **SDD's fix loop can decline a finding with evidence.** The resumed implementer verifies each task-review finding before fixing it. It declines a finding only as refuted or corrected, with file:line evidence. The scoped re-reviewer gains a DECLINED verdict, which it gives only after confirming that evidence; an unconfirmed decline stays NOT ADDRESSED. A round that declines every finding has no fix diff. It skips `review-package`, and the re-reviewer judges it from the evidence alone. The ledger's fix-round line becomes `(<X> addressed, <Y> declined, <Z> open — …)`. Measured on a new scenario, `sdd-fix-loop-refutes-wrong-finding`: both arms refuted the wrong finding with a verifying read in 10 of 10, so the change did not separate from control. Treatment also spent one extra procedural round in 9 of 10 trials. The change stays as guidance this measurement could not separate. The next fixture needs a finding whose refutation takes judgement rather than a lookup.
- **Plans cite the code they tell the implementer to imitate.** `writing-plans` adds a `## Grounding` section to the plan header. It gives one real `path:line` for each convention the work touches (at minimum naming, error handling and test shape), or `none: no existing pattern for <convention>`. A task may carry an optional `**Mirror:**` line naming code to imitate. If earlier tasks moved that code, the implementer re-locates it by the construct it names. The implementer prompt says to read a named Mirror before writing. A citation that does not resolve is a plan failure, and the self-review gains a fourth check, "Grounding is real". Unmeasured.
- **Plans and specs name their unknowns.** `writing-plans` sanctions one form of unknown: `Unknown:` or `Assumption: <what>, validate via <method>, before Task N`. The method is a specific check, and Task N is the first task that depends on the answer. A validation that fails is a plan conflict for the human partner, and bare TBD and TODO remain plan failures. `brainstorming` writes an unconfirmed premise in the spec as `Assumption: <what>, validate via <method>`. Unmeasured.
- **After compaction, the session-start hook names the plan's SDD ledger.** When SessionStart's source is `compact`, the hook adds one line naming the newest `progress.md` under the repo's SDD cache key, so a resumed controller reads its ledger instead of re-dispatching finished tasks. The hook:
  - reads the stdin payload once, bounded at two seconds, before the janitor forks;
  - re-derives the cache key itself rather than calling `sdd-dir`, so the lookup writes nothing;
  - skips paths that are not valid UTF-8;

## 6.11.0 (2026-08-26)

Subagent-driven development's progress record and evidence discipline, a new controller-fix carve-out, and two test suites that could report PASS without observing anything.

- **The ledger — not conversation memory — is SDD's progress record.** The implementer's agent identity is written into the ledger when the dispatch returns, so a controller resuming after compaction can still resolve fix-loop rounds 1-3 to the agent that did the work instead of dispatching a stranger. Todos mirror the ledger where they are surfaced rather than competing with it, and resume now classifies an in-flight dispatch instead of reading a task with no completion line as never started.
- **A covering command that cannot fail is not evidence.** Every implementer and fix dispatch names either a real covering command or an explicit `no covering command: <rationale>` line plus the controller's substitute verification; a dispatch naming neither is malformed. The controller re-runs the named command itself before acting on any completed-status report — the worked example now shows that re-run before both the review and the re-review.
- **De-minimis controller-fix carve-out.** When a task-review finding leaves no judgment — a typo, a constant the plan states verbatim, a one-line revert — the controller may apply it in its own session rather than pay a full implementer dispatch. The exception is fenced on every side: it is disclosed in the ledger, it consumes a fix round like any other and is counted everywhere that price is quoted, the covering command runs *before* the commit, the fix is committed before its scoped re-review, and two consecutive uses escape back to a dispatched implementer. A failing covering command means the fix was never de minimis: revert, spend no round, and go back to the round's own rule — which at rounds 4-5 is a fresh takeover implementer on a more capable model, not the original one that rule had already replaced.
